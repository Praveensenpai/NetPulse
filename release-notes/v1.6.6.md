# NetPulse v1.6.6

**Changing the device time zone no longer freezes *Today*. The app follows the new day immediately, without a restart.**

### 🐛 Fixed

- **Usage stayed on yesterday's bucket after a time zone change.** The reader side pinned `ZoneId.systemDefault()` when the screen subscribed; the writer re-read the zone on every call. Travel from Los Angeles to Kolkata, or change the zone by hand, and the two sides targeted different day keys. New traffic landed in a bucket the UI treated as future-dated, so Today, This Week and This Month all hid it until the app restarted.
- **The fix:** `DayKeys.dayKeyTicker` now takes `zoneProvider: () -> ZoneId` instead of a captured `zone: ZoneId`, and resolves "today" live on every 30 s tick. Both read paths (`observeDailyUsage`, `observeUsageHistory`) pass `ZoneId::systemDefault`, the same source `getTodayKey()` already used on the write path, so the two cannot disagree again.

### ✅ Verified

Measured on `emulator-5554` with the seeded ledger `usage_2026-11-01_mobile = 7,000,000` and `usage_2026-11-02_mobile = 1,000,000`. The zone was switched with `service call alarm 3 s16 Asia/Kolkata` while the process stayed alive (pid 21104 before and after), the same procedure that reproduced the defect on v1.6.5:

| Step | v1.6.5 | v1.6.6 |
|---|---|---|
| Start in `America/Los_Angeles` | Today `6.7 MB` | Today `6.7 MB` |
| Switch to `Asia/Kolkata`, process alive | Today **still** `6.7 MB` | Today `977 KB` |
| Upload 24 MiB after the switch | invisible in Today | Today `977 KB / 25.6 MB`, Total `26.5 MB` |

The stored protobuf agrees byte for byte: `usage_2026-11-02_wifi = 26,813,072`, `lifetime_wifi = 26,813,072`, `wlan0` tx delta `26,423,396`. A new `DayKeysTest` case pins the behaviour by holding the instant fixed and changing only the zone, so only the provider can explain the new key. 78 unit tests, 0 failures; 0 lint errors on debug and release.
